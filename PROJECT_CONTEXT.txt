DOCUMENTO DE CONTINUIDAD DEL PROYECTO OFERTAPP — Aplicación web de
descuentos para Uruguay

OBJETIVO DE ESTE DOCUMENTO Este documento sirve como contexto e
instrucciones para que otro agente de IA pueda continuar el desarrollo
de OfertApp sin depender de la conversación anterior. El agente debe
leerlo completo, revisar el repositorio y continuar desde el estado real
de los archivos. No debe asumir que una funcionalidad está terminada si
no puede comprobarlo.

============================================================ 1. VISIÓN
GENERAL DEL PROYECTO
============================================================

Nombre provisional: OfertApp

OfertApp es una aplicación web para descubrir descuentos y promociones
de supermercados, tiendas de ropa, marcas, farmacias, comercios de
electrónica, hogar, deportes y otros establecimientos.

Mercado inicial: Uruguay. Expansión futura: otros países. La
arquitectura debe permitir agregar países, ciudades, monedas e idiomas
sin tener que rehacer la aplicación.

Propuesta de valor: - Los usuarios indican qué marcas, comercios y
categorías les interesan. - Los comercios o administradores publican
descuentos. - La aplicación identifica qué ofertas coinciden con las
preferencias de cada usuario. - En una etapa posterior, los usuarios
reciben notificaciones push personalizadas.

La aplicación se desarrolla como proyecto de práctica y portfolio. El
usuario quiere que un agente de IA genere la mayor parte del código y lo
guíe paso a paso, con explicaciones claras y sin exigir conocimientos
avanzados de programación.

Idioma de la interfaz: español, con vocabulario natural de Uruguay (por
ejemplo, “Encontrá”, “Buscá”, “descuentos”). Moneda inicial: peso
uruguayo (UYU), mostrado como “$”. Diseño: moderno, limpio, minimalista,
responsive, con predominio de blanco y violeta.

============================================================ 2.
TECNOLOGÍAS Y ARQUITECTURA
============================================================

Tecnologías previstas: - HTML5 para la estructura. - CSS3 para estilos y
diseño responsive. - JavaScript para interacción y lógica del
frontend. - Git y GitHub para control de versiones. - GitHub Pages para
publicar la web estática. - Supabase, en una etapa posterior, para
autenticación, base de datos y servicios backend. - Un proveedor o
servicio compatible con notificaciones push web cuando se implemente esa
etapa.

Restricciones y decisiones importantes: - GitHub Pages aloja archivos
estáticos. No ejecuta código backend ni administra por sí solo usuarios,
contraseñas, procesos programados o notificaciones. - Nunca guardar
contraseñas, claves secretas ni credenciales privadas en el código
frontend o en el repositorio. - Para autenticación real, persistencia
multiusuario, permisos y datos compartidos se deberá usar Supabase u
otro backend adecuado. - Las notificaciones push requieren HTTPS,
permiso explícito del usuario, service worker y un
proveedor/infraestructura compatible. No prometer notificaciones hasta
que estén implementadas y probadas. - La primera versión es una demo
frontend con datos ficticios. No confundir datos de ejemplo con ofertas
reales. - Mantener la solución sencilla al principio. Evitar frameworks
complejos salvo que exista una razón concreta y el usuario acepte el
cambio. - No introducir dependencias o servicios pagos sin explicar
antes sus costos y alternativas. - Preparar el proyecto para escalar
internacionalmente: los registros de usuarios, comercios y descuentos
deberán relacionarse con país y, cuando corresponda, ciudad y moneda.

============================================================ 6. MODELO
DE DATOS PROPUESTO
============================================================

Diseñar las relaciones pensando en Supabase/PostgreSQL. No almacenar
listas complejas de marcas/categorías como texto separado por comas si
se necesitan relaciones consultables.

Tablas sugeridas:

countries - id - name - iso_code - default_currency - default_language -
active

cities - id - name - country_id

profiles - id (relación con el usuario de autenticación) - full_name -
country_id - city_id - role (user, merchant, admin) -
notifications_enabled - created_at

categories - id - name - slug - active

merchants - id - name - description - logo_url - country_id - city_id
(nullable si opera a nivel nacional) - address - website - active

brands - id - name - logo_url - category_id (si corresponde) - active

merchant_brands (si se necesita relación muchos-a-muchos) -
merchant_id - brand_id

discounts - id - title - description - image_url - discount_type
(percentage, fixed_amount, other) - discount_value - original_price -
discounted_price - currency_code - starts_at - ends_at - active -
country_id - city_id (nullable para ofertas nacionales) - merchant_id -
brand_id (nullable) - category_id - terms - external_url - created_at

user_brand_preferences - user_id - brand_id

user_category_preferences - user_id - category_id

favorite_discounts - user_id - discount_id - created_at

notifications (registro/historial; no necesariamente el envío en sí) -
id - user_id - discount_id - sent_at - read_at - status

Reglas: - Un usuario puede seguir muchas marcas y categorías. - Una
marca puede tener muchos descuentos. - Un comercio puede publicar muchos
descuentos. - Una categoría puede tener muchos descuentos. - Una oferta
puede ser nacional o estar limitada a una ciudad. - Todos los descuentos
deben tener país y moneda. - Definir índices y restricciones de unicidad
cuando corresponda. - En Supabase, configurar Row Level Security (RLS)
antes de usar datos reales. - Un usuario normal solo debe poder leer y
modificar sus propios datos privados. - Un comercio solo debe poder
administrar sus propios descuentos. - Solo administradores autorizados
pueden administrar catálogos globales o aprobar promociones.

============================================================ 7. LÓGICA
DE OFERTAS Y PREFERENCIAS
============================================================

La lógica futura de coincidencia debe contemplar: - La oferta coincide
con una marca seguida por el usuario, o con una categoría elegida. - El
país de la oferta coincide con el país del usuario. - Si la oferta tiene
una ciudad específica, coincide con la ciudad del usuario. Si city_id es
null, puede considerarse nacional dentro del país. - La oferta está
activa y dentro del período de vigencia. - El usuario tiene habilitadas
las notificaciones. - El usuario no debe recibir duplicados de la misma
oferta. - Deben existir límites de frecuencia y preferencias de horario
para evitar spam.

Antes de enviar una notificación, comprobar vigencia, coincidencia,
permisos y deduplicación. No implementar envíos desde el navegador
usando secretos expuestos.
